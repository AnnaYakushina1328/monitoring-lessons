# Развёртывание платформы мониторинга качества учебных занятий

## 1. Общая информация

**Проект:** Мониторинг качества учебных занятий.

**Организация:** ГБПОУ города Москвы «Московский колледж бизнес-технологий».

**Репозиторий:** https://github.com/AnnaYakushina1328/monitoring-lessons

**Назначение:** веб-платформа для планирования посещений учебных занятий, проведения экспертной оценки преподавателей, формирования результатов и анализа качества образовательного процесса.

### Технологический стек

- Python 3.13
- Django 5.2 LTS
- PostgreSQL 17
- Docker и Docker Compose
- Gunicorn
- WhiteNoise
- Nginx
- HTTPS / TLS

### Основные возможности

- Управление пользователями и ролями.
- Ведение справочника преподавателей.
- Планирование посещений занятий.
- Оценивание по шести специализированным чек-листам.
- Поддержка очных и онлайн-занятий.
- Сохранение черновиков оценивания.
- Формирование результатов.
- Ознакомление преподавателей с результатами.
- Мониторинг, аналитика и диагностика.

## 2. Архитектура

Предполагаемая схема:

```text
Пользователь
    |
    | HTTPS (443)
    v
Nginx + TLS
    |
    | HTTP на localhost:18000
    v
Docker: Django + Gunicorn
    |
    | Внутренняя Docker-сеть
    v
PostgreSQL 17
    |
    v
Docker volume: postgres_prod_data
```

Nginx обслуживает HTTPS-соединения и передаёт запросы приложению.

Gunicorn запускает Django в production-режиме.

PostgreSQL хранит пользователей, преподавателей, посещения и результаты оценивания.

База данных не публикуется в интернет.

## 3. Требования к серверу

Рекомендуемая конфигурация для первоначального пилотного запуска:

- Linux (например, Ubuntu Server LTS).
- 2 vCPU.
- 4 ГБ оперативной памяти.
- От 30 ГБ дискового пространства с запасом для БД и резервных копий.
- Docker Engine и Docker Compose Plugin.
- Git.
- Nginx.
- TLS-сертификат.
- Доменное имя с настроенной DNS-записью.

Указанные ресурсы являются стартовой оценкой. Итоговые требования необходимо уточнить после проверки фактической нагрузки.

## 4. Получение проекта

Подключиться к серверу по SSH и выполнить:

```bash
git clone https://github.com/AnnaYakushina1328/monitoring-lessons.git
cd monitoring-lessons
```

Для production рекомендуется развёртывание зафиксированного релиза или конкретного коммита, а не произвольной текущей версии ветки.

## 5. Настройка переменных окружения

Создать файл:

```bash
cp .env.prod.example .env.prod
```

Открыть `.env.prod` и установить реальные значения:

```dotenv
DJANGO_SECRET_KEY=REPLACE_WITH_LONG_RANDOM_SECRET
DJANGO_DEBUG=0

DJANGO_ALLOWED_HOSTS=monitoring.example.ru
DJANGO_CSRF_TRUSTED_ORIGINS=https://monitoring.example.ru

DJANGO_TRUST_PROXY_SSL_HEADER=1
DJANGO_SECURE_SSL_REDIRECT=1
DJANGO_SECURE_COOKIES=1
DJANGO_HSTS_SECONDS=0

POSTGRES_DB=monitoring
POSTGRES_USER=monitoring
POSTGRES_PASSWORD=REPLACE_WITH_STRONG_PASSWORD
POSTGRES_HOST=db
POSTGRES_PORT=5432
```

`monitoring.example.ru` приведён только как пример. Фактический домен должен быть согласован с организацией.

### Обязательные требования

1. Использовать уникальный криптографически стойкий `DJANGO_SECRET_KEY`.
2. Установить надёжный пароль PostgreSQL.
3. Указать фактический домен в `DJANGO_ALLOWED_HOSTS`.
4. Указать HTTPS-адрес в `DJANGO_CSRF_TRUSTED_ORIGINS`.
5. Не включать `DJANGO_DEBUG=1` на публичном сервере.
6. Не публиковать `.env.prod` в Git.
7. Ограничить доступ к файлу окружения средствами операционной системы.
8. Настроить защищённое резервное копирование.

Включение `DJANGO_TRUST_PROXY_SSL_HEADER=1` допускается только при доверенном обратном прокси, который самостоятельно устанавливает или перезаписывает заголовок `X-Forwarded-Proto`.

## 6. Проверка конфигурации Docker Compose

Перед запуском проверить конфигурацию:

```bash
docker compose --env-file .env.prod -f compose.prod.yaml config --quiet
```

Если ошибок нет, можно переходить к сборке.

Важно: вывод полной конфигурации Docker Compose может содержать значения переменных окружения. Не публиковать его в открытых журналах или переписке.

## 7. Сборка и запуск

Запустить контейнеры:

```bash
docker compose --env-file .env.prod -f compose.prod.yaml up -d --build
```

При предусмотренной конфигурации выполняются:

- запуск PostgreSQL;
- проверка доступности базы;
- применение миграций Django;
- сбор статических файлов;
- запуск Gunicorn.

Проверить состояние контейнеров:

```bash
docker compose --env-file .env.prod -f compose.prod.yaml ps
```

Просмотреть последние сообщения приложения:

```bash
docker compose --env-file .env.prod -f compose.prod.yaml logs --tail=100 web
```

При ошибке запуска необходимо установить причину, а не удалять тома PostgreSQL или повторно импортировать данные.

## 8. Настройка Nginx

Контейнер приложения должен слушать только локальный интерфейс сервера:

```text
127.0.0.1:18000
```

Nginx будет перенаправлять запросы на этот адрес.

Пример фрагмента конфигурации внутри HTTPS `server`:

```nginx
location / {
    proxy_pass http://127.0.0.1:18000;

    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

Необходимо:

1. Настроить DNS-запись домена.
2. Создать серверный блок Nginx.
3. Получить действующий TLS-сертификат.
4. Настроить HTTPS на порту 443.
5. Организовать перенаправление HTTP на HTTPS.
6. Проверить проксирование запросов.
7. Ограничить доступ к внутренним портам.
8. Убедиться, что PostgreSQL недоступен извне.

Полная конфигурация Nginx зависит от инфраструктуры организации.

## 9. Проверка безопасности Django

Выполнить:

```bash
docker compose --env-file .env.prod -f compose.prod.yaml exec web python manage.py check --deploy
```

Проверить предупреждения и устранить применимые проблемы безопасности до открытия публичного доступа.

Отдельно проверить:

- `DEBUG=False`;
- корректный `ALLOWED_HOSTS`;
- доверенные CSRF-источники;
- безопасные cookie;
- HTTPS-перенаправление;
- корректную работу CSRF-защиты;
- отсутствие открытых отладочных интерфейсов;
- ограничение доступа к административным разделам;
- права файлов и каталогов на сервере.

После настройки HTTPS следует рассмотреть включение HSTS. Сначала проверить правильность HTTPS для используемого домена, затем выбрать соответствующий период действия.

## 10. Статические файлы

В production-конфигурации предполагается использование WhiteNoise.

При запуске приложения выполняется:

```bash
python manage.py collectstatic --noinput
```

Проверить отображение:

- CSS-стилей;
- главной страницы;
- форм посещений;
- чек-листов;
- страниц результатов;
- мониторинга;
- диагностики.

Если часть интерфейса отображается без оформления, необходимо проверить `STATIC_ROOT`, настройки WhiteNoise и результат `collectstatic`.

## 11. Первоначальная настройка базы данных

Миграции Django создают структуру таблиц, но не заполняют автоматически все прикладные справочники.

Перед использованием необходимо подготовить:

- учётные записи пользователей;
- роли и права доступа;
- справочник преподавателей;
- шаблоны чек-листов;
- необходимые параметры системы.

В проекте предусмотрены шесть типов чек-листов:

| Код | Тип |
| --- | --- |
| `pd` | Теоретическое занятие |
| `lpz` | Лабораторно-практическое занятие |
| `oup` | Общеобразовательное занятие |
| `uppp` | Учебная / производственная практика |
| `attestation` | Аттестация студентов |
| `online` | Онлайн-занятие |

Применение команд импорта и генерации справочников необходимо согласовать с разработчиком.

Повторный запуск команд импорта без изучения их поведения может привести к дублированию, изменению или удалению данных.

## 12. Перенос существующих данных

Если необходимо сохранить локально созданных преподавателей, пользователей и результаты оценивания, перенос должен выполняться отдельно от GitHub.

Рекомендуемый подход — защищённый перенос PostgreSQL с проверкой совместимости версий приложения и структуры базы.

Требования:

1. Создать резервную копию исходной базы.
2. Подготовить защищённый канал передачи.
3. Исключить публикацию дампа в репозитории.
4. Восстановить данные на сервере.
5. Проверить количество и целостность записей.
6. Проверить авторизацию.
7. Проверить связи между преподавателями и пользователями.
8. Проверить права доступа.
9. Проверить сохранность оцениваний.

При переносе паролей пользователей необходимо обеспечить защиту базы и исключить распространение исходных файлов с временными паролями.

## 13. Резервное копирование

Production-база хранится в постоянном томе Docker:

```text
postgres_prod_data
```

Необходимо организовать:

- регулярные резервные копии PostgreSQL;
- хранение копий вне основного сервера;
- шифрование резервных копий;
- контроль доступа;
- проверку успешности резервирования;
- периодическую проверку восстановления;
- согласованный срок хранения копий.

Важно: команда

```bash
docker compose -f compose.prod.yaml down -v
```

может удалить тома проекта и привести к потере рабочей базы.

Для штатной остановки нельзя использовать параметр `-v`.

## 14. Обновление приложения

Рекомендуемый порядок обновления:

1. Проверить состояние системы.
2. Создать резервную копию PostgreSQL.
3. Уточнить версию приложения для установки.
4. Проверить миграции и совместимость.
5. Получить новую версию исходного кода.
6. Пересобрать контейнеры.
7. Проверить журналы.
8. Проверить основные пользовательские сценарии.

Команда пересборки:

```bash
docker compose --env-file .env.prod -f compose.prod.yaml up -d --build
```

Перед обновлением необходимо убедиться, что выбранная версия проверена и предусмотрен план восстановления.

## 15. Диагностика

### Состояние сервисов

```bash
docker compose --env-file .env.prod -f compose.prod.yaml ps
```

### Журналы приложения

```bash
docker compose --env-file .env.prod -f compose.prod.yaml logs --tail=200 web
```

### Журналы PostgreSQL

```bash
docker compose --env-file .env.prod -f compose.prod.yaml logs --tail=200 db
```

### Проверка Django

```bash
docker compose --env-file .env.prod -f compose.prod.yaml exec web python manage.py check
```

### Проверка миграций

```bash
docker compose --env-file .env.prod -f compose.prod.yaml exec web python manage.py showmigrations
```

### Проверка дискового пространства

```bash
df -h
```

При обнаружении ошибок не следует удалять контейнерные тома или пересоздавать базу без актуальной резервной копии.

## 16. Приёмочные испытания

Перед предоставлением доступа методистам необходимо проверить:

### Авторизация и пользователи

- Вход администратора.
- Вход методиста.
- Вход преподавателя.
- Корректное разграничение доступа.
- Отсутствие доступа к чужим результатам.

### Посещения

- Создание очного посещения.
- Создание онлайн-посещения.
- Редактирование запланированного посещения.
- Назначение методистов.
- Корректную работу предупреждений о пересечениях расписания.

### Чек-листы

- Доступность всех шести шаблонов.
- Соответствие критериев утверждённым оригиналам.
- Правильность вариантов оценивания.
- Корректность максимальных баллов.
- Сохранение черновика.
- Завершение оценивания.
- Отображение результатов.

### Онлайн-занятия

- Автоматический выбор онлайн-чек-листа.
- Запрет несовместимых сочетаний формата и шаблона.
- Наличие критерия «Использование функционала ВКС».
- Корректное отображение всех этапов.

### Мониторинг и диагностика

- Отображение результатов.
- Расчёт показателей.
- Фильтрация.
- Графики динамики.
- Диагностические представления.

### Ознакомление преподавателей

- Просмотр собственного оценивания.
- Подтверждение согласия или несогласия.
- Сохранение комментария.
- Ограничение доступа к чужим оцениваниям.

## 17. Текущий статус

Проект подготовлен к внутреннему пилотированию.

Production-конфигурация должна быть дополнительно проверена непосредственно на целевом сервере.

До начала полноценной эксплуатации необходимо завершить:

- сверку шести чек-листов с утверждёнными PDF;
- функциональное тестирование;
- проверку безопасности;
- настройку HTTPS;
- проверку резервного копирования;
- приёмочные испытания с участием методистов.
